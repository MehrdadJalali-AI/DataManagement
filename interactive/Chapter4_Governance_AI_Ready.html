Section 2

Metadata management & data catalogs

A data catalog is a searchable inventory of an organization's datasets, built from their metadata. Anyone can discover what data exists, what it means and whether they may use it — without asking around. It combines business context (owner, description, glossary terms, sensitivity) and technical context (schema, location, update frequency, quality score).

"Dark data"Without a catalog, metadata exists but nobody can find it — teams rebuild datasets that already exist, or use the wrong one.

Real catalogs: DataHub (LinkedIn), OpenMetadata, Amundsen (Lyft), Databricks Unity Catalog, Microsoft Purview, Collibra.

Section 3

Data lineage & provenance

Lineage

How data moves through a pipeline: which step reads what, and writes where. Used for impact analysis: "what does this feed?"

Provenance

Where each value ultimately came from, and how it was produced. Used for root cause: "where did this number come from?" — increasingly expected by regulators for AI decisions.

Impact analysis: break something upstream

Pick an upstream event. The lineage graph shows every asset at risk, and where to detect it (Practical 1).

Each pipeline step emits such an event; a lineage server (e.g. Marquez) stitches them into one graph across tools.

Section 4

Data contracts

A data contract is a formal, versioned agreement between the team producing a dataset and the teams consuming it: schema, meaning and guarantees, written down.

✓ Schema stability

Columns and types don't change silently.

✓ Agreed meaning

Every field has one documented definition.

✓ A change process

Renaming a column becomes a negotiated, versioned change — not a silent break of five dashboards.

Contract checker
orders.contract.yaml 
# orders.contract.yaml (simplified)
dataset: orders
version: 1.2.0
owner: sales-data-team
schema:
  - name: order_id
    type: string
    required: true
  - name: amount
    type: decimal
    unit: EUR
    rule: '>= 0'
  - name: order_date
    type: date
    required: true
freshness: daily by 06:00
consumers: [sales-dashboard, churn-model]
The producer team ships a new batch with these changes:
Why it matters for AIML pipelines break on silent schema drift. With a contract, a producer cannot drop a column a production model uses without updating the contract (a new major version) and notifying consumers first.
Section 5

Data-quality monitoring & observability

The Chapter 2 KPIs now run automatically on every new batch (e.g. a Chapter 3 rule stops the pipeline if completeness < 98%). Observability goes further and tracks four signals over time — catching silent decay that no single test flags.

⏱ Freshness Did the data arrive on time?
📦 Volume Is the row count normal?
🧱 Schema Did columns or types change?
📊 Distribution Do values look as usual?
Monitoring dashboard

Tools: Monte Carlo, Soda, Elementary (for dbt), Great Expectations.

Section 6

Data ownership & stewardship

O Data Owner

Accountable for a dataset's quality, access rules and business meaning. Approves who may query the customer table.

S Data Steward

Day-to-day custodian of quality and documentation for a domain. Defines what "active customer" means and keeps it documented.

C Data Custodian

Manages technical storage, security and backups. Configures encryption and the backup schedule.

G Governance Manager

Sets organization-wide policy, standards and escalation paths. Decides the company-wide retention policy.

U Data Consumer

Analyst or ML engineer: uses data responsibly and reports issues. Flags a suspicious spike in nulls to the steward.

The loopConsumers report issues to the steward → the steward fixes and documents → the owner stays accountable.

Classify these data items

Six protection measures

1 · Encryption

Unreadable to unauthorized users. Passwords stored hashed.

2 · Access controls

Only approved users. Only HR opens salary files.

3 · Auditing & monitoring

Who viewed or changed what. Access logs.

4 · Training & awareness

People handle data safely. Spotting phishing.

5 · Anonymization

Remove/hide personal identifiers. Names removed before research sharing.

6 · Data loss prevention

Stop leaks. Confidential files blocked from outgoing email.

Anonymization lab — k-anonymity

Removing names is not enough: ZIP + birth year + gender can re-identify people. Apply techniques until every person is indistinguishable from at least k others (k-anonymity).

Section 9

Dataset documentation & versioning

D · Document it

A README / data dictionary: each column, its unit, source and known limitations — for someone who has never seen the data.

column: line_total
meaning: quantity × catalogue price, in euros
note: excludes quarantined orders
V · Version it

Tag each meaningful version so any past analysis — or model — can be reproduced exactly. Tools: Git tag, DVC, lakeFS.

Version timeline

Why both?Documentation without versioning goes stale; versioning without documentation leaves files nobody can interpret.

What's new: governance for AI (2024–2026)

EU law

EU AI Act, Article 10

Training, validation and test data for high-risk AI must be relevant, representative and, as far as possible, error-free and complete — with documented data-governance practices. Per the lecture: obligations for stand-alone high-risk systems apply from 2 Dec 2027 (moved from Aug 2026 by the Digital Omnibus).

Graph-based data representation

A graph represents data as nodes (entities) connected by edges (relationships), each with properties (key–value details). A natural fit when relationships matter as much as the data — social networks, recommendations, knowledge graphs, fraud rings.

Explore a tiny property graph
Click a node or a question.

Graph vs. relational databases

FeatureGraph databaseRelational database
StorageNodes and edgesTables and rows
QueryingGraph traversal (Cypher)SQL joins
PerformanceFast for deep, relationship-heavy queriesSlower as joins multiply
Best forSocial networks, fraud, recommendationsStructured, tabular records (finance)
ExampleNeo4j storing a social networkPostgreSQL storing an orders table

Property graphs vs. RDF & knowledge graphs

AspectProperty graphRDF / knowledge graph
Basic unitNode and edge with arbitrary key-value propertiesTriple: subject – predicate – object
SchemaFlexible, informal, per projectFormal ontologies (RDFS, OWL) define shared meaning
Query languageCypher, GremlinSPARQL
StrengthFast traversal for one applicationLinking and integrating data across organizations
ExampleA company's Neo4j recommendation graphWikidata; a hospital linking patients to a medical ontology
Rule of thumbMany joins across relationships → graph. Stable tabular records → relational. One application, fast traversal → property graph. Shared meaning across organizations → RDF + ontologies.

Try it live: Wikidata Query Service (SPARQL) · Neo4j Sandbox (Cypher).
