Reproducible & Validated Data Pipelines

In Chapter 2 you cleaned data once, by hand. Next month new files arrive. A pipeline runs the same cleaning the same way, every time, proves the result is right, and shows where every number came from.

Without validated, documented, version-controlled transformations → no trustworthy analytics.

Analogy: Cleaning in a notebook by hand is cooking from memory. A pipeline is a written recipe: anyone can cook it again, taste-test at each step (validation), and you never throw away the original ingredients (raw data).

Inputs & steps

Inputs — where data comes in
  • Raw files are read, never written
  • Read everything as text first, then convert types on purpose
  • Record which file every row came from — the start of lineage
Steps — what the pipeline does
  • One function = one job: clean, join, split or write
  • Steps run in a fixed order, each using the previous result
  • Small steps are easy to read, test and fix

for f in RAW.glob('orders_*.csv'):

Raw, clean & output layers

raw/

Files exactly as received: never edited, only read.

output/

Trusted, business-facing tables, ready for BI and AI.

Guiding ruleData flows one way: raw → clean → output. Never backwards, never overwriting raw. Each layer can be checked on its own — a cleaning bug is fixed once, and every output is rebuilt.

Section 5

Reusable cleaning functions — DRY

Don't Repeat Yourself: one function holds one cleaning rule and is called wherever it's needed. Fix a date bug once, in the function, and it's fixed everywhere — instead of in five copied notebooks.

def parse_mixed_date(col):
    iso = pd.to_datetime(col, format='%Y-%m-%d', errors='coerce')
    de  = pd.to_datetime(col, format='%d.%m.%Y', errors='coerce')
    return iso.fillna(de)

# used wherever dates appear:
orders['order_date'] = parse_mixed_date(orders['order_date'])
Test parse_mixed_date

Unparseable values become NaT (missing) instead of crashing — a later validation rule (nullable=False) then decides what happens to them.

Section 7

Failing safely — stop or quarantine

🛑 STOP the pipeline

A critical rule is broken — the whole table can't be trusted (e.g. duplicate order IDs). Nothing is written.

try:
    df = rules.validate(df, lazy=True)
except pa.errors.SchemaErrors as err:
    print(err.failure_cases)
    sys.exit(1)        # stop: write nothing
🗄 QUARANTINE rows

Only some rows are bad (e.g. unknown customer). Set them aside with a reason, keep the rest.

quarantine = df[df['reason'] != '']
clean      = df[df['reason'] == '']
quarantine.to_csv('output/quarantine_orders.csv')
Rule of thumbStop for problems that break the whole table; quarantine problems that affect single rows. Never a silent bad number on a dashboard.

-- models/marts/fct_orders.sql
SELECT o.order_id,
       o.order_date,
       o.quantity,
       p.price               AS unit_price,
       o.quantity * p.price  AS line_total,
       c.city
FROM   {{ ref('stg_orders') }}    o
JOIN   {{ ref('stg_customers') }} c ON o.customer_id = c.customer_id
JOIN   {{ ref('stg_products') }}  p ON o.product     = p.product
WHERE  o.quantity > 0
# models/marts/schema.yml
models:
  - name: fct_orders
    description: Trusted orders, one row per order
    columns:
      - name: order_id
        tests: [unique, not_null]
      - name: quantity
        tests:
          - dbt_utils.accepted_range: {min_value: 1}
      - name: city
        tests:
          - accepted_values:
              values: [Heidelberg, Mannheim, Karlsruhe]

Section 13

Discussion questions (Slido) — think first, then reveal

Why should a pipeline never edit the raw data files?

Raw data is the only ground truth. If a rule is wrong you fix it and re-run from raw; if raw was overwritten, the original information is gone forever and nobody can verify or reproduce the result.

A step joins clean orders and customers. Which layer does it belong in?

It reads from the clean layer and produces a business-facing, enriched table — so its output belongs in the output layer (e.g. fct_orders). It must never write back into raw.

Why automate validation instead of checking the data by eye?

Eyes miss things, get tired and don't scale to millions of rows or monthly runs. Automated rules run every time, check every row, report exactly what failed and are documented in code.

When should a pipeline stop, and when should it only quarantine a row?

Stop when the whole table becomes untrustworthy (duplicate IDs, missing columns, wrong schema). Quarantine when the issue is local to individual rows (unknown customer, negative quantity) — and keep the reason.

What does Git give you that a folder of final_v2.csv files doesn't?

History with authors and reasons, exact restore of any version, branches + review, CI tests before merge, and code/rules/docs versioned together.
