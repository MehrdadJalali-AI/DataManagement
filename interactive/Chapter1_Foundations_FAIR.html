Section 1

From raw data to value

Data management is the process of collecting, storing, organizing and maintaining data so it stays accurate, accessible, secure and usable. It is what turns raw data into decisions you can trust.

The one-line summary of the courseWithout data management → no reliable AI.

Inconsistent results

Two teams compute "monthly revenue" and get two different numbers. Nobody knows which one is right.

High costs

Errors, security gaps and re-work cost money. Gartner has estimated poor data quality costs organizations millions per year on average.

Limited reproducibility

A thesis result can't be repeated because the cleaned file was final_v3_NEW.xlsx on a laptop that no longer exists.

Unreliable AI/ML

Models inherit every flaw in their training data — missing values, bias, duplicates — and turn them into wrong predictions.

Accuracy

Correct, consistent data → decisions you can trust.

Reproducibility

Documented data and pipelines let anyone repeat and verify results.

Efficiency

Clean, well-organized data saves time in every later step.

Security & compliance

Controlled access protects sensitive data and meets rules like the GDPR.

Where you meet it in the real world

AI

Training ML models

A model is only as good as its data — this is where AI-ready data starts.

Research

Research data sharing

FAIR data lets teams and disciplines build on each other's work (e.g. COVID-19 genome sharing via GISAID / ENA).

Real-time

Real-time monitoring

IoT sensors, financial markets and live dashboards depend on timely, well-managed data streams.

Section 3

OLTP vs. OLAP — run the business vs. understand it

Organizations run two kinds of systems. OLTP creates the data, OLAP analyses it, and data management (ETL/ELT pipelines + metadata + quality checks + access control) is the bridge.

AspectOLTP Online Transaction ProcessingOLAP Online Analytical Processing
PurposeProcess day-to-day transactions in real timeAnalyse large volumes for reporting and decisions
WorkloadMany small, fast writes (INSERT/UPDATE)Few large, complex, read-heavy queries
DataCurrent, detailed recordsHistorical, integrated data
UsersClerks, customers, appsAnalysts, managers, data scientists
StorageRelational database (PostgreSQL, MySQL, Oracle)Data warehouse / lakehouse (Snowflake, BigQuery, Databricks)
Speed measured inMilliseconds per transactionSeconds–minutes over millions of rows

OLTP: one transaction

-- customer clicks "Buy" (runs in milliseconds)
BEGIN;
INSERT INTO orders(order_id, customer_id, total) VALUES (1042, 77, 59.90);
UPDATE stock SET qty = qty - 1 WHERE product_id = 'P-13';
INSERT INTO payments(order_id, method) VALUES (1042, 'card');
COMMIT;

OLAP: one question over millions of rows

-- "Sales trend by region?"
SELECT region,
       DATE_TRUNC('month', order_date) AS month,
       SUM(total) AS revenue
FROM   fact_orders
WHERE  order_date >= '2024-01-01'
GROUP BY region, month
ORDER BY month;

Analogy: ETL is a restaurant that washes and chops vegetables before they go into the fridge. ELT puts all the groceries in a huge fridge first and prepares them when a recipe needs them — you can always re-cook from the original ingredients.

Section 5

Data warehouses, data lakes & lakehouses

Each architecture solved the main limit of the one before it: warehouses (1990s) were reliable but costly and structured-only → lakes (2010s) added scale and raw data but risked becoming a "data swamp" → lakehouses (2020s) add a metadata & governance layer (ACID tables) on cheap lake storage.

Aspect🏛 Data warehouse🌊 Data lake🏠 Lakehouse
StructureStructured only — schema-on-write (fixed first)Any format — schema-on-read (decide later)Raw + structured together
Primary useBI, dashboards, OLAPData science, ML, explorationBI and ML on one copy
CostHigher: curated, indexedLow-cost object storageLow cost, near-warehouse speed
GovernanceStrong, matureWeak — risk of a data swampACID transactions + governance
Example techSnowflake, Redshift, BigQueryAmazon S3, ADLS, HDFS + SparkDatabricks, Delta Lake, Apache Iceberg

Section 6

Varieties of data — the structure spectrum

Structured

Fixed schema: rows & columns

Orders, customers, payments. Stored in OLTP databases and warehouses. Easiest to query.

Semi-structured

Flexible, self-describing tags

JSON, XML, app logs, API responses. Stored in lakes / lakehouses.

{"user": "Anna K.", "device": "mobile",
 "tags": ["sale","new"], "rating": 5}
Unstructured

No predefined format

Emails, product photos, call recordings, PDFs. Stored in lakes. Most flexible, hardest to analyse — often ~80% of enterprise data.

Section 7

The FAIR principles

FAIR = Findable, Accessible, Interoperable, Reusable — guidelines for making data usable by people and machines, introduced by Wilkinson et al. (2016). The running example below is a (fictional) diabetes outpatient cohort.

FAIR ≠ openData can be FAIR even when access is restricted, as long as the rules for access are clear. Patient data is a perfect example.

Findable = persistent ID + rich metadata + searchable catalog. The DOI stays the same even if the files move; keywords and description let people and search engines find the dataset — without exposing any patient.

{
  "identifier": "https://doi.org/10.5281/zenodo.1234567",
  "title": "Type 2 Diabetes Outpatient Cohort, 2020–2023",
  "description": "Anonymized visit and treatment records of 1,250 patients",
  "keywords": ["diabetes", "metformin", "outpatient care"],
  "creator": "Example University Hospital",
  "temporalCoverage": "2020/2023",
  "registeredIn": "Zenodo"
}

Real-world: try searching Google Dataset Search — it only finds datasets that publish this kind of metadata.

Accessible = standard protocol + clear access rules + metadata that stays available. Anyone can see the metadata; only approved roles who accept the data use agreement can open the data.

{
  "identifier": "https://doi.org/10.5281/zenodo.1234567",
  "protocol": "HTTPS",
  "accessRights": "restricted",
  "authorization": "OAuth 2.0",
  "allowedRoles": ["Physician", "Approved researcher"],
  "dataUseAgreement": "Treatment and ethics-approved research only (GDPR)",
  "metadataAccess": "public and permanent"
}

Interoperable = standard format + shared vocabulary + linked references. HL7 FHIR defines the format, LOINC 2339-0 defines what "blood glucose" means, a standard unit removes guesswork.

{
  "resourceType": "Observation",
  "status": "final",
  "code": { "coding": [{ "system": "http://loinc.org", "code": "2339-0",
            "display": "Glucose [Mass/volume] in Blood" }] },
  "subject": { "reference": "Patient/P123456789" },
  "effectiveDateTime": "2023-01-15",
  "valueQuantity": { "value": 95, "unit": "mg/dL" }
}
GET [base]/Observation?patient=P123456789

Reusable = clear license + provenance + quality + documentation. A future user can judge and reuse the data without asking the original team.

{
  "identifier": "https://doi.org/10.5281/zenodo.1234567",
  "version": "3",
  "license": "Data use agreement: ethics-approved research only",
  "quality": "Glucose values checked against reference ranges",
  "documentation": ["README.md", "codebook.csv"],
  "provenance": {
    "source": "Electronic Health Record system",
    "steps": [
      { "date": "2024-02-01", "action": "Exported outpatient visits 2020–2023" },
      { "date": "2024-02-03", "action": "Removed names and addresses" },
      { "date": "2024-02-05", "action": "Converted to FHIR, coded with LOINC" }
    ]
  }
}

Benefits & challenges

Benefits

Efficiency — one documented, citable version instead of DATA_final_NEW.xlsx.
Visibility — "climate data Germany" returns 1 match instead of 0.
Collaboration — research, industry, academia and government build on a shared repository.
Reuse cycle — found → used → shared → new data → …

Challenges

Effort and cost of good metadata · lack of skills and incentives · privacy & legal constraints · many competing standards and vocabularies · legacy systems with no identifiers.

Section 8

DOIs — permanent addresses for data

A DOI (Digital Object Identifier) is a persistent identifier. Even if the file moves to another server, the DOI resolves to its current location via https://doi.org/.

Take a DOI apart

How to get a DOI

  1. Choose a DOI agency — DataCite (datasets), Crossref (publications)
  2. Register an account (or use a repository that does it for you)
  3. Prepare metadata — title, authors, date, …
  4. Submit resource + metadata
  5. Receive the DOI and use it to cite & share

Repositories that mint DOIs for you

ZenodoCERN; FAIR metadata, GitHub integration FigsharePublic items get a DOI DryadCitable research datasets DataverseHarvard's open data platform
Practical tipConnect your GitHub repo to Zenodo: every GitHub release then automatically gets its own DOI — perfect for citing the exact code + data version of your project.
Section 9

Metadata — the hidden part of the iceberg

Metadata is data about data. It describes and documents datasets so they are understandable, findable and reusable. Metadata = context + structure + meaning.

Descriptive title, author, abstract, keywords — what is it?
Structural file format, schema, column types, relationships — how is it organized?
Administrative access restrictions, license, versioning, retention — who may use it, and how?
Descriptive, structural or administrative?

Why metadata needs standards

If every team invents its own field names (author, creator, made_by…), machines can't combine catalogs. Standards give everyone the same vocabulary.

15 simple, general-purpose elements (title, creator, subject, description, date, format, identifier, rights, …). Used by libraries, museums, and as a baseline everywhere. DCMI Terms →

The standard behind DOIs for research data. Mandatory: identifier, creator, title, publisher, publicationYear, resourceType. DataCite Metadata Schema →

JSON-LD embedded in web pages, read by search engines (that's how Google Dataset Search works). schema.org/Dataset →
